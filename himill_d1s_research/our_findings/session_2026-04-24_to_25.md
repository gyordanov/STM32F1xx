# Session log: 2026-04-24 → 2026-04-25

## Topology in scope

```
[Sender / browser] ──WiFi──→ [ESP32 + ESP3D 3.0.0.b1] ──UART2──→ [STM32F103RC + grblHAL]
                                       ↑
                                       └─USB CDC (alternative path, host-driven)
```

ESP3D handles telnet (port 23), WebSocket data (port 8282), HTTP (port 80),
and ESP3D's internal WS (port 81 — for ESP3D-WEBUI's protocol). Bytes from
clients reach STM32 via UART2; bytes from STM32 reach clients via the same
UART2.

## The big debugging trail

### Symptom

Running `$esh` over telnet stops mid-output (~$486-490). On reconnect,
remaining settings drain followed by **2 banners** and an ignored first
command.

### Hypotheses tried (all wrong)

1. **Stream multiplexer broadcast bug** — fixed (single-stream routing) but
   $esh still stopped
2. **`?` polling stealing output** — tested on with strict-active-stream
   semantics; still stopped
3. **Button polling glitch** (PC4/PB1 noise during busy-wait firing
   spurious CMD_SAFETY_DOOR) — disabled polling, still stopped
4. **TX buffer overflow** — bumped 2KB → 8KB; stop point shifted from
   $486 to $490 (proportional to buffer size, suggesting the issue
   triggers right *as* blocking starts)
5. **UART baud bottleneck** — bumped 115200 → 460800; user reverted, not
   the cause
6. **DTR fluctuation from ModemManager** — disabled, still stopped
7. **DTR fluctuation from anywhere** — pulled USB cable, still stopped
8. **`linestate_event` hook scheduling banner via `output_welcome_message`**
   — set `state.linestate_event = Off`; **didn't fix the cascade**
9. **Hard-limit pin EMI** — set `$21=0`, still stopped
10. **E-stop pin EMI** (PB4 transient under UART noise) — set
    `CONTROL_ENABLE=0`, **still stopped**

### What actually worked

`USB_SERIAL_CDC=0` (USB CDC stack compiled out entirely). With this build,
`$esh` completes cleanly. Mux/no-mux, buttons-on/off — none of those
mattered. Only USB CDC presence.

### What this means

The reset cascade is somehow **caused by USB CDC stack being active**, not
by anything in our wrappers. Possible mechanisms:
- USB IRQ priority interaction with UART2 IRQ (both at priority 1)
- USB peripheral generating phantom interrupts during long UART activity
- Hardware-level coupling (USB clock affects something else)
- A grblHAL code path that's only active when both streams registered

Per the agent research (see `our_findings/agent_esp3d_research.md` if it
exists, or run the same query): ESP3D doesn't proactively send anything to
UART. The 2-second-then-banner pattern matches ESP3D-WEBUI's `?;[ESP701]json`
polling delay — but `[ESP*]` is filtered by ESP3D before forwarding, and
`?` is just a status query. So the ESP3D-WEBUI hypothesis doesn't hold up
on its own; something STM32-side is the real trigger.

### Cosmetic fix that worked

`[ESP*]` consumer in `himill_user_command` eats the polling probe so
grblHAL doesn't emit `error:1` to clients. Before fix: clients saw
`error:1`. After fix: clients see no response (silent ignore). Senders
prefer the latter.

## MaxMake's likely architecture (informed speculation)

Their custom `DS:<bits>` realtime status field reported door, e-stop,
3D-probe state as polled bits. That's noteworthy because it would mean
those signals **aren't bound to grblHAL CONTROL inputs** in their build.

If correct: their solution to the EMI / reset-cascade problem was to
**not let those pins trigger grblHAL's `mc_reset()` chain at all**.
Senders read state via `DS:` polling instead. No edge-triggered IRQs
for safety door / e-stop / probe-disconnect → no `mc_reset()` storm
during long output.

This would also explain why MaxMake's e-stop "just stopped the machine"
without going into "crazy estop state" — they handled e-stop in
application code, not via grblHAL's hard-error path.

If we want to fully match (or beat) MaxMake's UX without `USB_SERIAL_CDC=0`,
the path forward is:
1. Disable grblHAL CONTROL bindings for the noise-prone pins
2. Add a polled status report extension that surfaces them as bits
3. Handle "e-stop pressed" in our `himill_d1s.c` realtime hook —
   transition state ourselves rather than calling `mc_reset()`

## Hardware specifics

- TMCs in STANDALONE mode; PD2 is the silent/fast toggle. Fan runs always
  → user opted for fast-mode-permanent at boot rather than per-job toggle.
- USB-VBUS not connected to anything critical (board needs mains). USB
  cable is data-only. Plugging it in doesn't power the board, doesn't
  switch primary stream — only a host *opening* `/dev/ttyACM0` does (DTR).
- ST-LINK flash MUST use `--freq=100`. The default ~1MHz hits a flash
  loader bug on STM32F103RC where the loader's stack lands in
  non-existent SRAM (st-flash assumes 64KB; chip has 48KB). 100 kHz
  works around it.

## Things that didn't work and why

- `MPG_ENABLE=2` — toggles streams via 0x8B byte; ESP3D doesn't auto-send
  it (verified in source); useless without manual user trigger
- Direct `memcpy(&hal.stream, target, ...)` switching — broke USB
  enumeration (clobbered something during init); reverted to wrapper
  approach which works for stream switching but doesn't fix the
  reset-cascade
- Dropping into `stream_connect()` to switch primary at runtime — would
  re-emit "TELNET STREAM ACTIVE" type messages and add to connections
  list with each call (potential leak)
